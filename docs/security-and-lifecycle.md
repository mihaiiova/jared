# Local authority, execution and retention

## Local-only boundary

Local stdio MCP clients are trusted **same-user operators**, not tenants. They can approve/register a caller-supplied local Git root through `setup_project`, then submit work against its exact locally present commit. Every task, result lookup, cancellation and acknowledgement requires a project ID; a job ID from another project returns `not_found_or_denied`. Project routing prevents accidental workspace/report mix-ups, not malicious same-user access. No caller cwd is inferred. No bearer tokens, admin roles, network listeners, HTTP transport, remote registration, SSH keys, Git network fetch or tunnels remain active.

The official MCP v2.4 `serveStdio`, `StdioServerTransport` and `McpServer.registerTool` serve each connection over a private Unix socket; the public `jared mcp` executable is a stdio byte bridge. The socket is mode 0600 inside mode-0700 private state. A detached internal worker starts on demand. Only that worker holds the crash-released SQLite EXCLUSIVE-transaction ownership lock (`owner.sqlite`, separate from job storage) and SQLite writer; racing frontends connect to the winning owner instead of failing a global client lock. No public TCP listener or manual daemon is needed. The worker exits after all clients disconnect and jobs/source reads/registrations settle, but remains the owner while stop confirmation or source reconciliation is required. Frontends retry an exited starter within a bounded 10-second connection window; failure identifies the last starter exit or unavailable socket. A slow live starter is not duplicated. Detached jobs survive stdio disconnect; worker crash/restart behavior is different and described below. No hostile same-UID race or malicious process-group escape containment is claimed.

## Native assets and loadout

`agent/v1/` contains unchanged approved native Jared system/settings, policy, reviewer definition and six skills. `provenance.json` records each SHA256. Build verifies them; `node scripts/assets.mjs /approved/source/root` explicitly re-exports only these files after matching the approved hashes. Normal builds and packed installs need no sibling checkout, Faur, runtime asset generation, `.pi/npm`, global configuration, sessions or auth. The package's source-audit capability is deliberately narrower than the reusable assets' implementation skills.

Each role gets a new native Pi 1.5.2 subprocess, in-memory session, host UUID and private HOME/Pi directory outside the worktree. The environment is built from scratch: package-owned target-specific search bin plus fixed system PATH/LANG, private HOME/Pi, guard receipt, and exactly the explicit key or consented native Codex auth file pointer. No product/global Pi resources or unselected auth, arbitrary worker environment, cloud keys, proxies, NODE_OPTIONS, MCP, browser tooling or ambient extensions are inherited. The only explicit extension is the package-owned audit guard. Its receipt must prove the expected cwd and exact `read,ls,find,grep` tool set before a prompt is sent. The guard refuses external, traversal, Git-metadata and symlink paths. Repository instructions remain untrusted data; no shell, setup, tests, edits, delegation or product MCP are enabled. This is not an OS sandbox; trusted local Git repositories/configuration are assumed.

Lead policy is the non-derived portion of bundled `.pi/APPEND_SYSTEM.md` plus `ui-audit`. Reviewer policy is the bundled `ui-reviewer` definition plus `ui-evaluate`; their hashes are retained in result provenance. A broad derived capability list is not enabled. Both get only a neutral source packet (purpose, task, platform, approved direction, scope, exact SHA/design paths); reviewer receives no lead narrative, draft report, self-rating, transcript or reasoning. Fresh host run IDs differ. Other bundled skills remain available as native assets but do not enable implementation jobs. No role/skill definitions or Faur code are changed by this package.

The executor uses native typed Pi JSONL RPC because the SDK RpcClient's merged environment, unowned child and stderr forwarding do not meet these process/credential constraints. It attaches listeners before sending commands, verifies the guard, requires prompt `started` acceptance, `agent_settled` and final assistant `stop`. Exit zero or settlement alone is not delivery. Protocol/output is bounded; stderr and provider exception bodies are not echoed. Reports return as JSON text to the host, not through agent file-writing tools.

## Local exact-commit snapshots and reports

Git uses fixed `/usr/bin/git` argv and a minimal environment: no hooks/fsmonitor/global config/credential helper, redirects, automatic prompts or submodules. Only file transport to an approved canonical local root is permitted; HTTPS/SSH/other protocols are disabled. The full lowercase 40-character SHA must already be a commit in that root. The private job bare repository imports that object, verifies exact type/SHA, keeps a ref and creates a dedicated detached worktree. Original branches, tracked/staged/unstaged/untracked content are never included implicitly or edited by an audit. Unpushed commits are supported. Local Git is not a sandbox for hostile repository config or same-user filesystem interference.

Only explicit setup writes `.jared/config.json`, `.jared/.gitignore` and `.jared/runs/` in the original project. Conflicts, symlink roots/state, hardlinked config, tracked run artifacts and pre-existing job report directories are refused; writes use exclusive file creation. Repeating `setup_project` with the same project ID and root can update metadata (recorded as `project_metadata_updated`) and recreate a removed `.jared` directory; it cannot change the registered root or overwrite conflicting files. Partial/ambiguous state (for example, retained runs without their config marker) still requires explicit operator repair. Missing state returns `project_state_missing_run_setup_project`. Reports are copied to **that project's** `.jared/runs/<jobId>/{audit.md,reviewer-report.md,result.json,status.json}`. Private raw receipts, packets and retained snapshots stay in user state. Failed/cancelled jobs get available status/evidence, not fabricated reports. Publication failures fail task delivery; an unavailable project status copy is logged durably without deleting private evidence.

Host validates report schema/size/regular single-link path containment, job/SHA linkage and cited paths as exact-commit regular blobs (not symlinks, <=256 KiB). It checks worktree Git linkage, SHA and cleanliness including ignored/untracked files before/after both roles. Raw adapter run receipts are diagnostic trusted-executor evidence, not independently re-read as a second security boundary. Lead-policy hash is not in the current result schema. Source coverage, findings and subjective judgments are agent-reported, not exhaustively proven. Audit findings (including blockers) are compatible with delivered audit output. `visualVerification` is always `not_run`; overall verification is `partial`, never a visual/runtime pass.

## Queue, cancellation, disconnect and restart

SQLite is authoritative for registry, idempotency, job states/events/results, source receipts and acknowledgement. Scheduling keeps at most two combined active jobs/source reads and serializes audits per project; up to 100 outstanding local jobs are allowed. `(project,local identity,idempotencyKey)` is unique: identical canonical input returns the existing job, different input conflicts. Source cache initialization is commit-addressed; conflicting/capacity-exhausted reads fail busy rather than racing.

The default 120-second running deadline covers local snapshot preparation and both sequential roles; queue time is excluded and unbounded. Git operations also have a 15-second bound. No provider-backed evidence supports tuning this default yet.

Accepted jobs continue after stdio EOF/close/SIGTERM of a frontend; reconnecting retrieves the same durable jobs. The worker does not exit merely because its last client disappeared during work. When the **worker** shuts down, active execution is aborted and awaited; stopped interrupted jobs are `crashed`, not caller cancellations. Queued jobs remain durable. A hard crash releases the kernel owner lock. On restart, Linux boot ID/PID start receipts identify owned process groups; still-matching groups are killed and confirmed stopped, then running jobs become `crashed` with no replay. On macOS, `ps` supplies group/state/start data and `sysctl` supplies the boot-session UUID. Start timestamps have only second precision, so macOS receipts are additionally scoped to the owning service process. A different owner after a hard crash cannot prove a live group's identity: it retains `stop_unconfirmed` or source reconciliation rather than signalling the group. After the operator verifies/stops the actual orphan and restarts Jared, dead groups are reconciled without replay. Normal in-owner cancellation and orderly shutdown still stop owned groups. Native macOS verification is pending.

Ambiguous live groups are never killed speculatively: `stop_unconfirmed`/source reconciliation blocks scheduling and requires operator intervention. Queued jobs may resume. Unconfirmed orphaned source rows are retained without preventing worker startup. They record a `source_reconciliation_required` event under `source:<readId>` in private SQLite; queued jobs expose the same diagnostic and cannot run. Context reads are also blocked. The owner stays alive until operator intervention and restart confirms termination; it never kills an identity-mismatched group.

Cancellation/deadline sends RPC abort, then TERM/KILL to the whole owned process group. Cancellation success is reported only after executor/group termination; unconfirmed stops retain `stop_unconfirmed`. Ordinary descendant/process-tree termination and hard-crash reconciliation are tested offline; malicious `setsid` escape and live provider cancellation are not demonstrated. OAuth workers allow a 17-second TERM grace for bounded refresh persistence; Git/API-key grace remains short. Shutdown/cancellation never deletes dirty or undelivered work.

## Selected native Pi auth

Catalog-discovery restrictions do not disable provider/model internet requests or native OAuth refresh. API-key CLI workers pass `--offline` to suppress startup catalog/tool network operations without blocking inference; Codex SDK workers retain the selected-provider-only, no-catalog-network guard below. Doctor remains no-network. Search binaries are part of the installed package, with pinned upstream archive and binary checksums plus licenses under `vendor/tools/`. Setup, doctor and workers use only that package's OS/CPU tools, never PATH/Pi-cache discovery or a mutable legacy helper cache. Normal installation/setup performs no separate helper download. The explicit maintainer-only vendor refresh is not an npm lifecycle hook. Existing legacy caches are retained but unused; package damage requires reinstallation rather than another setup/download attempt. Setup and doctor check native tool execution; worker readiness checks integrity before accepting model work. No global resources/auth are imported with tools.

OAuth uses public `ModelRuntime.create({authPath, modelsPath:null, allowModelNetwork:false, refreshOnCreate:false})`, native `login` and services/RPC. There is no custom CredentialStore, refresh protocol, token copy, per-job auth symlink or global worker Pi directory. Every role retains its private HOME/Pi directory and unchanged source guard/tools/resources.

Default setup offers the selected provider's existing Pi OAuth login with explicit shared-write consent. Missing auth offers bundled SDK login; dedicated mode is advanced. Config holds only the auth-source kind/path. Safe regular owner-controlled, single-link, canonical, non-world-readable files outside checkouts/assets/job state are required. The shared parent may contain normal Pi files and need not be 0700; it cannot be group/world writable. The selected entry must be native Codex OAuth, never an API-key command. Other provider entries are accepted without resolution/use.

Pinned SDK services otherwise refresh availability for all providers during bootstrap. A narrow per-instance public `refresh` override forces `providers:["openai-codex"]` and `allowNetwork:false`, retaining native AuthStorage while preventing unrelated command/API-key resolution. No prototype/global patch or resource-discovery change is used. Detection and doctor use the SDK's one-off `readStoredCredential` (no command resolution, lock, network or write).

Native AuthStorage holds its cross-process proper-lockfile lock around latest read, SDK refresh and merged write. Other provider records survive semantically unchanged, not necessarily byte-for-byte formatting. It writes the file **in place**, not atomic rename/fsynced persistence. The SDK has a 30-second lock wait/stale interval; interrupted rotation or power loss may require new login. Cancellation once refresh starts permits native credential persistence; process termination still has bounded grace and cannot guarantee recovery. Setup refuses auth-source changes while an owned worker holds its lock, with no speculative process killing or state reset.

API-key alternatives retain the explicit external private-file behavior; no ambient keys are borrowed. Secrets and source artifacts remain same-user sensitive. No live login/provider entitlement or audit-quality verification was performed.

## Retention and migration

There is **no TTL, quota or automatic destructive pruning**. Failed, cancelled, timed-out, interrupted, dirty and unacknowledged work remains private. Explicit project/job `acknowledge_handoff` with `acknowledged` requires a delivered result; `abandoned` can retire a stopped failed/cancelled worktree. Both refuse changed SHA, dirty/untracked/ignored data, symlinks or changed Git linkage. Git removes only the clean owned worktree without force. Bare repos/keep refs, raw/validated evidence, SQLite findings/events, source caches and product run reports remain. Repeated acknowledgement is safe. Monitor disk space externally; never delete live state/lock inodes as a repair strategy.

Before upgrading a Linux `flock` installation to this revision, stop existing Jared workers/jobs. The older lock protocol does not coordinate with `owner.sqlite`; do not run old/new workers against the same state. Do not delete either live lock inode.

Old remote-prototype private config/auth/state and the external source archive are preserved untouched, not migrated or reused. New local state uses `jared-local` directories. HTTP/token/admin/SSH implementation/provisioning tests and docs were removed, not hidden behind local defaults. Old listeners/client entries need explicit operator retirement; setup does not alter them.

Unsupported: implementation/code writing, credentialed branch delivery/push, merge/deploy, remote execution, runtime/browser/Flutter/catalog verification, public exposure, hostile-code isolation and mutation replay. Live login/entitlement/provider audit quality remain unverified; no provider/product workload was run to implement this iteration.
